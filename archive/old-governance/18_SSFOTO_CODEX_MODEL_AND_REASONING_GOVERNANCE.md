# 18_SSFOTO_CODEX_MODEL_AND_REASONING_GOVERNANCE.md

Version: 1.0  
Status: Active  
Purpose: Codex model selection, reasoning level, token discipline, and execution efficiency governance for SS Foto.

## 1. Purpose

This file defines how Codex should choose the right reasoning level and working mode before executing any SS Foto task.

Codex must read this file before starting any task.

If the current session is too long or context is unreliable, Codex must recommend a new session before starting a new implementation batch.

The goal is to keep execution accurate, safe, auditable, and token-efficient.

SS Foto project is currently focused on the public website:

- SEO website
- UI/UX rebuild
- local service funnel
- Google Business Profile support
- WhatsApp conversion
- upload/order entry point
- tracking foundation
- redirect/indexing cleanup
- future ecommerce foundation

Do not overthink simple tasks.
Do not underthink architecture, routing, SEO, schema, or tracking tasks.

## 2. Mandatory Pre-Work Checklist

Before starting any task, Codex must identify:

1. Task type
2. Risk level
3. Required reasoning level
4. Required files to read
5. Forbidden scope
6. Expected output
7. Verification method

Codex must not begin implementation until this assessment is clear.

## 3. Reasoning Level Selection

Use the lowest reasoning level that can safely complete the task.

### Low Reasoning

Use for:

- copy text changes
- CTA label updates
- simple metadata updates
- small link fixes
- small component styling
- typo correction
- straightforward redirect addition
- simple sitemap entry adjustment

Rules:

- Read only directly relevant files.
- Keep response short.
- Do not audit unrelated areas.
- Do not propose architecture changes.

### Medium Reasoning

Use for:

- route creation
- page implementation
- metadata/canonical alignment
- schema addition
- sitemap/robots updates
- WhatsApp/upload CTA context
- event tracking implementation
- branch page creation
- local service page creation
- productized page creation
- internal linking updates

Rules:

- Read project instruction and relevant project files.
- Inspect existing patterns before editing.
- Make minimal safe changes.
- Verify routes, metadata, and links.
- Report changed files and remaining issues.

### High Reasoning

Use for:

- URL strategy conflicts
- redirect/canonical conflicts
- sitemap/indexing cleanup
- duplicate/cannibalization decisions
- route architecture changes
- analytics event architecture
- schema architecture
- multi-page batch implementation
- migration from old structure to approved structure
- owner-decision conflicts
- security/privacy/isolation work

Rules:

- Read all directly relevant governance files.
- Identify conflicts before editing.
- Stop and report if owner decision is needed.
- Do not make destructive changes without approval.
- Produce a structured patch report.

### Deep Reasoning

Use only for:

- major architecture revision
- cross-system planning
- future phase planning
- ecommerce/payment architecture
- WABA CRM architecture
- toko app architecture
- BIS architecture
- DealPOS integration design
- broad SEO strategy change
- project file rewrite

Current public website implementation should rarely need Deep Reasoning.

Deep Reasoning is not allowed for routine page edits.

## 4. Model / Intelligence Usage Principle

Codex must choose the most efficient capable model.

Use higher intelligence only when the task has:

- architectural risk
- SEO indexing risk
- route/canonical conflict
- data privacy risk
- multi-file dependency
- unclear owner decision
- irreversible or destructive operation
- tracking/schema complexity

Use normal/efficient intelligence when the task is:

- limited
- low-risk
- single-file
- already specified
- purely mechanical
- easy to verify

Do not use high intelligence just because the task is long.
Use high intelligence when the task is risky.

## 6. Token Efficiency Rules

Codex must:

- avoid rereading unrelated files
- avoid repeating full project file contents in reports
- summarize findings, not dump full code
- keep patch reports concise but complete
- avoid speculative architecture discussions during implementation tasks
- avoid broad audits unless specifically requested
- avoid fixing unrelated problems
- avoid scope creep

If a task is large, Codex must break it into smaller execution batches.

## 7. Implementation Discipline

Codex must execute in small, auditable steps.

For each implementation task:

1. Inspect relevant files.
2. Identify existing patterns.
3. Apply minimal patch.
4. Verify.
5. Report.

Codex must not:

- rewrite large files unnecessarily
- remove working content without approval
- change approved URL strategy
- create unapproved pages
- implement future scope
- silently change business logic
- silently change tracking taxonomy
- silently change schema strategy
- silently change sitemap strategy

## 8. Conflict Handling

Codex must stop and report before implementation if it finds:

- conflict between project files and repo state
- conflict between approved URL and existing route behavior
- missing redirect destination
- duplicate canonical target
- sitemap includes non-canonical URLs
- public page depends on internal/future route
- potential privacy issue
- potential destructive deletion
- need for owner decision

Codex report format for conflict:

- Conflict found
- File/location
- Project rule
- Repo reality
- Risk
- Recommended options
- Owner decision needed

## 11. Verification Rules

Codex must verify changes using the safest available method.

Preferred verification:

- source inspection
- route/file existence check
- sitemap inspection
- robots inspection
- redirect config inspection
- metadata inspection
- schema inspection
- TypeScript check if safe
- build if safe
- lint if non-interactive

If a check fails due to pre-existing unrelated errors, report clearly:

- command run
- failure summary
- why it is unrelated
- whether current task is still safe

Do not fix unrelated TypeScript/internal errors unless assigned.

## 12. Destructive Change Rule

Codex must not delete, move, or mass rewrite files without explicit owner approval.

Examples requiring owner approval:

- deleting /admin
- deleting /internal
- deleting /toko
- deleting old public SEO pages
- removing upload/order flow
- changing canonical URL strategy
- changing route taxonomy
- removing productized pages
- replacing service page content wholesale

For now, prefer:

- redirect
- noindex
- isolate
- report
- owner approval

## 13. Batch Size Rule

Codex should avoid large mixed-scope tasks.

Good batch examples:

- Fix URL redirects and sitemap only.
- Create branch pages only.
- Create local pas foto pages only.
- Create local cetak foto pages only.
- Add tracking events only.
- Add schema to branch pages only.

Bad batch examples:

- Redesign homepage + add schema + create all local pages + tracking + sitemap.
- Rewrite all service pages and modify redirects in one task.
- Build ecommerce while fixing SEO routes.

## 15. Context / Session Management

Codex must manage context carefully across long SS Foto work sessions.

A long or noisy session increases risk of:
- applying outdated assumptions
- missing current project scope
- mixing completed tasks with new tasks
- over-reading files
- making unsafe implementation decisions
- wasting tokens

Codex must recommend starting a new session before beginning a new implementation batch when the current session becomes too large or unreliable.

### Start a New Session When

Recommend a new session when:

- prior conversation context has become long, noisy, or mixed with unrelated topics
- multiple implementation tasks have already been completed in the same session
- the next task is a new scope batch
- Codex would need to reread many files because current context is unreliable
- implementation risk increases due to context crowding
- the user asks for a major new task after several completed patches
- the task shifts from audit to implementation
- the task shifts from one domain to another, such as redirects -> branch pages -> tracking -> schema
- unresolved blockers or owner decisions are mixed with old context
- the session contains outdated instructions that may conflict with the latest governance files

### Do Not Start a New Session For

Do not recommend a new session for:

- small follow-up questions
- clarifying one patch report
- validating one changed file
- continuing the same small task
- explaining the next step

### Before Moving to a New Session

Before recommending a new session, Codex must provide a compact handoff summary:

1. Completed tasks
2. Files changed
3. Current repo state
4. Unresolved blockers
5. Owner decisions needed
6. Next recommended task
7. Exact project/governance files to include or read in the next session
8. Any commands that failed because of pre-existing issues

### New Session Starter Format

When starting a new session, Codex should ask the user to include this context:

- Project: SS Foto public website Phase 1
- Active scope: public website SEO, UI/UX, local funnel, WhatsApp/upload foundation, tracking, redirects/indexing
- Must read:
  - Project Instruction
  - 00_SSFOTO_DOCUMENT_INDEX_AND_GOVERNANCE
  - 18_SSFOTO_CODEX_MODEL_AND_REASONING_GOVERNANCE
  - task-relevant files only
- Current task ID
- Last completed task summary
- Remaining blockers

### Rule

Codex must not continue a risky implementation task if the session context is too crowded to reason safely.

In that case, Codex must stop, summarize, and recommend a clean new session.
